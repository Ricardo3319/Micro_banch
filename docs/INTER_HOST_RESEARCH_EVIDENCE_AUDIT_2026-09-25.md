# 主机间研究方向的实验依据复核

日期：2026-09-25。方式：代码静态核查、已有 CSV/报告核对和负载口径推导；未修复代码或重跑实验。目的：判断哪些证据可以支持选题，避免将模型问题误判为算法天花板。本文件不替代后续实验验证。

## 1. 相同 seed 并非相同请求轨迹

证据：[初始化与负载生成](../src/core/simulator.cpp#L104)、[生成器](../include/sim/workloads/generators.h#L10)、[调度抽样](../src/core/simulator.cpp#L366)。`PoissonArrival`、`MMPPArrival`、`BimodalService`、`LognormalService` 持有同一个 `rng_` 的引用；调度选目标、刷新热点以及初始化周期检查的随机偏移也消费它。

因此算法不同会改变随后负载随机序列，连“同一 seed 的 W2 突发位置”也不保证相同。现有 3/5、5/5 胜负是记录的数值关系，不能解释为同一到达样本的配对收益。它不证明算法无效，但削弱小样本因果解释。

建议预生成并冻结 `arrival_time/request_type/service_demand/payload/affinity/capacity_change` 轨迹，按内容哈希核对；为算法内部随机化另设随机数流。外生热点及容量变化也必须独立于调度决定。使用同轨迹的成对差值和独立运行间区间；不应把同一次运行的一百万条请求当一百万个独立实验。

## 2. 名义 ρ 低估实际占核负载

证据：[到达率公式](../src/core/simulator.cpp#L104)用 `rho * effective_capacity / 24`；[执行时间](../src/core/simulator.cpp#L494)为 `base_service_us / capacity + T_host_us`；[常数](../include/sim/common/constants.h#L5)中 `T_host_us=2.1`。

对同构 `capacity=1`，实际平均占核时间为 24+2.1=26.1 μs：

`rho_cpu = rho_nominal * 26.1 / 24`。

- W1 名义 0.95 → 实际 offered load 1.033125。队列长期无法稳定，不能描述成严格稳定的 95% 利用率。
- W2 名义 0.85 → 正常阶段 0.924375；乘 1.5 的突发阶段约 1.386563。它同时包含全局到达强度变化与热点分发。
- 按 MMPP 设计的平均驻留时间 5000/500 μs，长期到达倍率约为 1.04545，W2 上述名义 0.85 的平均 CPU offered load 约 0.96639。这是参数的稳态近似，并非有限运行的实测利用率。

异构场景必须按每类核心的 `E[S]/capacity+2.1` 分别核算吞吐，不能只把核速度求和后仍除以 24。

因此旧报告中 W1 全部或接近全部违约有容量口径上的解释；零迁移只说明该实现拒绝动作，不证明最优的过载控制，也不证明预测有效。

## 3. 目标核心预规划在到达路径中被丢弃

证据：[handle_task_arrive](../src/core/simulator.cpp#L420)。释放预留后先将 `reserved_dst_core=-1`，再检查此字段是否有效来选择核心。对进入释放分支的正常已预留迁移，后面的预规划核心分支不会执行。

这不等价于“所有迁移都失败”：请求仍进入 `shortest_queue_core()` 选出的队列。但实际放置与评分/预留所依赖的核心安排不同，不能据此证明目标计划准确。应先保存计划核心、完成必要校验与放置，再清理字段；随后重测受影响机制。

## 4. 非 oracle 模式还存在未来信息

证据：[estimate_service_time](../src/core/simulator.cpp#L236)和[Core::local_workload_us](../include/sim/model/core.h)。默认服务估计为 oracle；类别均值、EWMA、分位数保护模式依据真实 `base_service_us` 是否超过 20 μs 来选类别。运行任务的残余工作量来自真实 `finish_time_us-now_us`。

类别若来自 RPC opcode 或可见参数，可以作为合法输入；当前代码从最终实际服务时间推导类别，不能自动等同于应用可见类型。尤其在 W3 连续分布中，两者不同。

应将可见类型、预测服务时间和实际服务时间分离；残余时间依据已运行时间与观测分布估计。oracle 保留作乐观参考，运行时算法不能读取模拟器掌握的未来事件。

## 5. 即时全局预留不等于可部署的跨主机协议

证据：[批次计划](../src/core/simulator.cpp#L1445)读取全局 `incoming_reservation_`；[迁移提交](../src/core/simulator.cpp#L1606)即时累加目标预留，随后在 `now+T_net_oneway_us` 到达。控制器没有经过网络获得目标确认。

这相当于模拟器提供一个即时串行协调点。若部署为分布式源端控制，必须实现接收确认、预发额度或其他一致的额度机制，并计入反馈过期、并发争抢、有效期和在途请求。一次迁移限制也不会自动保证网络重试下只执行一次。

同一流程需要明确：请求从 `QUEUED` 原子转为 `TRANSFERRING` 时工作线程不能再领取；确认、超时和重试由谁持有执行权。首个原型可以先在无主机崩溃条件下验证所有权唯一，故障语义另行明确。

## 6. 负载构造与算法知道的场景标签

证据：[热点分发](../src/core/simulator.cpp#L337)在 W2 突发时按 `w2_hot_dispatch_prob` 将请求限制到热点候选；默认值 0.5。[DQB 路径](../src/core/simulator.cpp#L1342)根据 `workload_type_` 修改饱和阈值和允许批次数，并为 W3 选择不同候选构造。

热点限制可以是压力测试或副本亲和约束，但要说明现实来源。如果请求只能在热点副本执行，迁移算法也必须遵守相同合法目标集合；如果所有目标都可执行，则需比较没有这项人为限制的强入口。

运行时不能免费知道这是“W1/W2/W3”。按真实场景标签选择参数是工作负载特定策略；论文必须明确其信息条件，或改为由可观测特征推断并在未见轨迹验证。

## 7. 当前队列结构与拟议模型不同

证据：[Node](../include/sim/model/node.h)、[Core](../include/sim/model/core.h)、[到达分发](../src/core/simulator.cpp#L451)。当前主机包含 16 个核心队列，新请求到达后立即分配到一个核心；DQB 通常从核心队列构造批次。

“主机共享 NIC/入口队列，核心空闲才领取”会消除一部分核心间排队失衡，同时改变候选任务和源等待估计。它是新的排队模型，不能只改图中队列标签。应先用简单共享队列确定跨主机积压是否仍存在，再决定如何复用批量算法。

## 8. 成本与测量窗口

证据：[迁移到达事件](../src/core/simulator.cpp#L1625)主要增加固定 3.15 μs；[运行终止](../src/core/simulator.cpp#L204)以完成计数达到目标为准。

每 1 μs 构造摘要和候选的成本、目标确认、字节传输、PCIe/DMA、源/目标代理占核与拥塞尚不能由这个常数代表。指标中累计的估算成本也不能自动当作已在执行关键路径支付的开销。

完成计数窗口可能留下不同的未完成请求集合。需要固定到达窗口并排空测量，或者明确记录窗口末积压、超时与删失；过载测试尤其不能以“较快完成的一部分请求”的尾延迟代表全体请求。

## 对旧结果的使用建议

原始 CSV 和汇总保持可追溯，暂称“旧模型下的探索结果”。先解决随机轨迹、负载口径和目标放置，再解决观测权限与通信代价，最后加入强基线。顺序的意义是先判断收益是否可信，再讨论算法是否复杂得有必要；本次核查没有给出修正后数值。
