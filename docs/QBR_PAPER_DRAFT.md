# 通信成本约束下的跨主机微秒 RPC 队列放置与批量重调度

**状态：研究稿，2026-09-26；包含已完成仿真证据，未完成真实系统评测，不是可直接投稿的论文。**

## 摘要草稿

微秒级 RPC 调度通常同时面对负载反馈滞后、主机服务能力变化和严格的通信预算。将已分发的排队请求主动迁移到其他主机可以修正失衡，但其收益依赖可移动队列长度、目标接收能力和协调路径。本文构造具有主机共享队列、有限候选摘要和显式 CPU/网络成本的离散事件模型，设计接收额度约束的批量纠偏算法 QBR，并与强入口工作量调度、有界入口排队、批量工作窃取及单请求纠偏比较。使用冻结轨迹完成 1800 次主实验和 2840 次敏感性/消融运行。结果显示：在当前参数范围内，批量纠偏相对无纠偏工作量入口的收益有限且不稳定，无法在多数条件下超过有界入口排队；高总请求率也未形成足够大的可迁移批次。研究结果支持进一步评估队列放置、反馈新鲜度与额度流水深度的共同作用，并明确跨主机真实实现所需验证的成本边界。

## 1. 问题与相关工作

研究对象是同机架副本服务上的无状态请求。执行中的任务不迁移；服务类别对调度器可见，但实现不读取未来完成时间。固定核心数和额外控制核心构成统一资源预算。

RackSched 说明跨主机入口与主机内执行需要协同。R2P2 的 JBSQ 将部分等待留在入口，减少过早绑定。Rain 的 token 队列、分类和动态 worker 额度构成当前直接近邻。Altocumulus 已提出主动迁移及低开销机制，不能将主动或批量本身列为新贡献。Breakwater 则表明额度和通信摊销早已用于微秒级 RPC 准入。[RackSched](https://www.usenix.org/system/files/osdi20-zhu.pdf)、[R2P2](https://www.usenix.org/conference/atc19/presentation/kogias-r2p2)、[Rain](https://arxiv.org/abs/2606.03352)、[Altocumulus](https://www.eecg.utoronto.ca/~mcj/papers/2022.altocumulus.micro.pdf)、[Breakwater](https://www.usenix.org/system/files/osdi20-cho.pdf)。

本文当前能成立的贡献是可审计比较和机制边界识别。候选算法是否具有独立新颖性和系统价值，必须在真实路径及更强近邻下继续证明。

## 2. 假设与研究问题

- RQ1：强入口策略下，分发后队列还保留多少可移动、可获益的工作量？
- RQ2：在真实协调路径下，单请求与有界批量纠偏各自的控制成本和尾延迟如何？
- RQ3：目标预留是否提供可测量的独立收益，还是主要保证协议协调？
- RQ4：全局容量不足、局部失衡和服务时间长尾是否要求不同队列机制？

“把主机抽象成网卡队列”只确定逻辑队列位置。仿真使用软件共享 FIFO，并显式建模核心速度和运行中工作量预测；没有声称能忽略主机内部变化。

## 3. QBR 设计

源端周期检查增量工作量和队首年龄，对连续压力选择有限候选目标。批量工作量由两端流体排空时间差及通信余量决定。目标串行发放带过期时间的额度，源端收到后重新检查，从尚未执行的队尾请求中选择有界批次。载荷到达时消费额度，过期则退回。全部控制消息经过 CPU 与网络队列。

精确公式、状态机、费用口径和复杂度限制见 [算法说明](QBR_ALGORITHM.md)。流体准则不构成每请求完成时间或 P99 保证，这是解释负面结果的重要限制。

## 4. 实验方法

主实验包括平稳、25% 主机局部降速、单主机短暂停顿、全局突发和类内长尾服务。每个场景取 0.5/0.7/0.85/0.95 四档名义负载、10 个独立正式种子。到达与服务轨迹先生成并记录哈希，策略抽样不会改变负载。预热 5 ms，统计之后 20 ms 内到达的请求并完全排空。

所有策略执行相同应用服务时间，网络与 CPU 费用在模型中计入。主指标为分类型 SLO 违约率、P99 和吞吐；P99.9、迁移比例、反事实迁移质量、批次大小、控制 CPU 与通信量共同报告。区间以种子配对 bootstrap 计算；多重比较未校正，结果用于机制探索。

基线是协议范围透明的策略复现，没有用缩减实现冒充原论文全系统。两个额外候选 `work/bwc` 的完整失败结果同样保留。

## 5. 已观察结果

在负载 0.85、局部容量下降时，QBR 与 JSW 的 SLO 违约率分别为 26.529% 和 26.572%；差值 −0.042 个百分点的区间跨零。JBSQ 为 16.910%。在单主机短暂停顿、负载 0.70 时，QBR 相对 JSW 有约 0.055 个百分点改善，但相对 JBSQ 的差值区间跨零。

QBR 并未稳定超过简单阈值批量或批量窃取。负载 0.85 下成功批次平均仅约 1.6–2.3 个请求。不同算法引起后续排队轨迹变化，被迁移请求的反事实延迟比较需要谨慎解释；当前高“无改善迁移比例”不应被隐藏，也不能解释为严格的单次迁移因果效应。

JBSQ 深度为 1 时，反馈往返产生的供给空档可以导致吞吐损失；深度增大又可能加重主机等待。敏感性实验进一步表明网络、入口 CPU 和总体容量余裕必须与队列深度一起分析。

## 6. 效度威胁

当前使用合成负载、短统计窗口和配置中的类别先验；本地容量变化对本地主机可知。没有真实请求数据依赖、NUMA、缓存失效、NIC DMA、丢包或崩溃恢复。运行中剩余工作量的先验下限可能造成误判。专用控制核、全局入口搜索及聚合网络端口需要真实成本验证。

20 ms 到达窗口与 10 个种子适合发现机制问题，不足以支持长期稳定性或稀有尾部承诺。CloudLab 测量器是校准准备，不是已完成的调度系统。

## 7. 当前结论

目前应保留跨主机问题和共享队列抽象，将批量重调度视为有条件的辅助机制。现有证据不能支持“高任务量自然要求大批迁移”或“QBR 已优于有界入口调度”的结论。后续真实系统验证应先对齐通信成本与队列位置，再判断是否存在足够的、可稳定复现的迁移空间。
